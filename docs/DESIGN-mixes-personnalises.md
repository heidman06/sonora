# Design Sonora — « Tes Mix » façon Spotify + filtres personnalisés — rév. 2 (normatif)

> Rév. 2 corrige les 22 constats Goldfish de la rév. 1 (archivée dans l'historique de session). Chaque correction est référencée [Cn]. Ce document est la référence d'implémentation de la v2.4.0.

## 1. Objectif et non-objectifs
Rangée horizontale de mixes personnalisés par compte : 8 à 12 quand le corpus le permet, 15–60 titres selon le corpus [C7], covers mosaïque 2×2, noms/sous-titres localisés ×3, calcul sans appel réseau bloquant, warm borné daily-only ; points d'entrée de recherche personnalisés par compte et par langue. Non-objectifs : pas de mix Nouveautés daté ni horaire ; pas de reranking Piped ni réordre Library ; pas de migration legacy (/mixes garde le contrat v1, React consomme /mixes2) [C3] ; zéro diff engine internals/audio.mjs/hls.mjs/index.mjs/sw.js/subsonic.mjs/web-legacy/* ; mixes non éditables ; promesse de volume honnête : corpus ≥ 40 distincts ⇒ ≥ 8 mixes ; 10–39 ⇒ mixes maigres réels ; < 10 distincts ⇒ 3 coquilles génériques localisées [C8].

## 2. Contraintes et invariants
C1 deps npm inchangées ; frontend/package.json inchangé ; racine : seule la ligne scripts.check étendue à musique-mixes.mjs [C4]. C2 pool yt-dlp ≤ 2 finally. C3 premier GET /mixes2 : 0 spawn/0 réseau attendu ; jamais await recos(). C4 isolation userDuToken + WHERE user_id ; track_meta joint seulement par LEFT JOIN sur des videoIds déjà dans le corpus du compte [C12]. C5 cache client jamais purgé au logout, clés sonora.u.<user>.*, SW jamais /api/*. C6 i18n durci ×3. C7 home row-scroll ≤ 12 cards, skeletons, pas de liste verticale. C8 hermétique YTDLP=/bin/false PIPED='' + SONORA_MIX_WARM='0'.
I1 contenu neutre en langue ; graines génériques = clés neutres favorites|history|playlists|rotation|bulk [C14] ; cache serveur clé userId sans lang. I2 déterminisme deux temps : ensemble = tri SQL stable + troncature AVANT tirage ; tirage seedé (userId, seedJour UTC, mixKey) ne fait que permuter ; aucun Math.random/ORDER BY RANDOM dans le builder [C5]. I3 musique-moods : défauts inchangés ; ajouts = paramètre pool, exports POOL_NEUTRE et toucherMoods (algorithme partagé, pas dupliqué) [C18]. I4 epoch anti-résurrection : mixEpoch incrémenté à chaque purgeMixes ; warm capture l'epoch et n'écrit que si inchangé ET ligne présente (UPDATE sans INSERT) [C2]. I5 budget warm : ≤ 1 job actif tous comptes, file ≤ 2, ≤ 4 ytsearch40 × 30 s ⇒ ≤ 120 s, 1 slot ; le warm ne relance JAMAIS lancerRecos [C1][C10]. I6 cooldown warm 6 h/compte ; déclencheur = daily émis count < 50 ; hit de cache frais ne déclenche rien [C9]. I7 mixes() v1 et mixes2() partagent builder et cache ; v1 = adaptateur pur (3 mixes, noms FR historiques, tracks ≤ 20) [C3].

## 3. Décisions
X1 catalogue : module pur server/musique-mixes.mjs ; corpus unique 10 SQL (affinites ; likes LEFT JOIN track_meta tri added_at DESC, video_id ASC LIMIT 200 ; history 90 j COALESCE(h.duration, tm.duration) tri at DESC, id DESC LIMIT 600 ; playlist_tracks LEFT JOIN track_meta tri position LIMIT 400 ; boucle GROUP BY c DESC, video_id ASC LIMIT 60 ; archives < -90 j LIMIT 120 ; rejetes ; lireRecos lecture seule ; mix_cache lecture+écriture) ; plafond testé 12 (marge 2) [C12] ; corpusDistincts = Set JS (0 SQL) [C8].
Catalogue : deco (toujours si ≥ 1 ; recos + complément corpus seedé, ni secours() ni RANDOM) ; boucle (≥ 5 distincts c ≥ 2, ordre COUNT desc) ; favoris (likes ≥ 3, troncature 50 puis permutation) ; daily1..4 (ancres affinites p ≥ 6 escalier p ≥ 4, dédup normaliserArtiste, plancher 10, titres de l'ancre + recos seed === ancre) ; mood1..4 (score neutre ≥ 8 escalier ≥ 4, moodNew exclu, plancher 15, touching partagé + artistes ARTIST_MAP) ; archives (≥ 30 distincts > 90 j) ; escalier rotation (≥ 10 distincts history 90 j) / vrac (≥ 10 playlists).
Anti-doublon [C22] : Jaccard > 0.8 ⇒ suppression du moindre prioritaire (ordre deco, favoris, boucle, daily, mood, archives, rotation, vrac) ; deco exempté (mix découverte, recouvrement assumé) ; corpus mono-artiste ⇒ < 8 mixes assumé.
Score neutre [C18] : POOL_NEUTRE = union par id des 3 pools, tags union dédupliquée, q = entrée FR (non utilisé par le builder) ; toucherMoods exporté et partagé ; caps 24/12 inchangés ; seuils 8/4 validés par fixtures.
Cold [C8] = corpusDistincts < 10 ⇒ 3 coquilles {key cold1..3, labelKey = moodId, moodId, subtitleKey mixColdSub, tracks []}.
Noms/sous-titres [C14] : XOR strict subtitleKey/seeds ; seeds typés {t:'key'|'artist', v} ; vocabulaire fermé mappé ×3 (seedRotation/seedBulk nouveaux) ; mixLabel : branche coquille (labelKey === moodId) puis mixMoodName({mood}) puis mixDailyName({n}) puis tr(labelKey) [C20]. Cover = min(4, tracks.length) [C13].
X2 cache : table mix_cache(user_id PK, json, at, seed) ; v DANS le JSON ; garde v + seed === seedJour UTC + age < 45 min sinon reconstruction ; persistance = survie au redémarrage DANS le TTL [C17]. Purges = 7 sites utilisateur exacts (playlist DELETE, tracks POST, bulk, tracks DELETE, like POST, like DELETE, feedback) + ecrireRecos ; epoch++ à chaque purge [C19][C1]. pousseHistory ne purge pas. Warm : ecrireWarm gardé epoch + UPDATE conditionnel [C2] ; cooldown 6 h [C9] ; jamais lancerRecos [C1] ; internes getters vivants ytActifs/warmLances/compteSqlMixes/mixEpoch + hook purgeMixes + ecrireWarm [C11][C6].
X3 UI : row-scroll + MixArt mosaïque 2×2 (4 img lazy) ; ≤ 12 cards ≈ 108 nœuds ; effet mixes SÉPARÉ avec mixes/mixesLoading dédiés (skeleton 4 cards), le Promise.all recos/history conserve loading [C21] ; deps sans lang ; « Tout voir » → #/mixes (tab listen) ; MixesView grille pl-grid + détail TrackList memoryKey 'mixes.<key>' (rehydratation existante) ; porteur = snapshot mémoire module lib/mixes.ts, sinon localStorage, sinon refetch assumé en URL profonde [C15] ; clé inconnue → grille ; lecture playMix inchangée ; coquille cold → radio(q locale, 40) ; invité → #/library.
X4 recherche : filtres de type inchangés ; chips état vide plage 4–6 = top moods scorés ≤ 4 + artistes 0–2 via réponse /moods partagée (lireMoodsCache, un seul fetch si absent) ; repli statique = 6 premières moods du catalogue localisé [C16] ; CA localisation sur chips statiques cold (q[2] = rap français / hip hop rap / reggaeton 2026) [C16].
X5 offline : cache sonora.u.<user>.mixes {v, at, lastAccess, seed, resp}, garde v, LRU 6 n'évinçant jamais le courant, garde course peutEcrireMixes + alive ; échec → cache ; ni cache ni réseau → coquilles + mixesEmpty ; invité coquilles statiques zéro fetch/écriture.
X6 tests : §7.

## 6. Risques
R1 payload 75–90 Ko (LAN, SWR 1 fetch/montage, v1 ≤ 20 titres). R2 warm affame recos (I5 recalculé, test pool). R3 noms hétérogènes (groupage JS normalisé, plancher 10 + warm). R4 frontière UTC ≠ minuit local (documenté, seed dans réponse). R5 quota (LRU 6 ~450 Ko, try/catch, repli). R6 mixes maigres assumés (count réel, warm daily-only ≤ 120 s + cooldown). R7 Piped HS (complément corpus seedé). R8 GROUP BY sans index (< 5 ms [H], compteur, index en réserve). R9 régression legacy/recos/moods (adaptateur + suites vertes sans modification, smoke 15). R10 course (alive + peutEcrireMixes, effet sans lang). R11 EN→ES (mixMoodName fr=es≠en non flaggé). R12 cold offline radio échoue (toast unavailable, documenté). R13 mix_cache corrompu (garde v dans JSON + seed + TTL). R14 résurrection (epoch + UPDATE + test). R15 rebond (cooldown + test). R16 mono-artiste doublons (Jaccard + suppression, < 8 assumé). R17 URL profonde sans état (refetch assumé + skeleton).

## Écarts d'implémentation assumés (v2.4.0)

- Compte réel heid : 7 mixes à la livraison (corpus mono-dominant phonk) ; ≥ 8 garanti sur corpus diversifié (fixtures) ; escalier rotation/vrac appliqué.
- smoke prod : 15 checks (forme v2 /mixes2 ajoutée) ; le smoke repo se lance avec cwd=~/dashboard (chemins relatifs data/).
